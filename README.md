# rclone-sciebo-webdav

Mirror local git repositories and other directories to [sciebo](https://www.sciebo.de)
(a Nextcloud instance) with [rclone](https://rclone.org/webdav/), without clutter or
leftover temporary files. Per-source direction (`sync`, `pull`, or `bisync`), a manual
manifest, git-repo discovery, a Nextcloud-style folder chooser, clutter filters, and a
per-directory `.nosync` opt-out keep the setup small. `sciebo check` dry-runs
everything; `sciebo sync` applies; one run at a time via a lock. Optional daily launchd
agent, on-demand `rclone nfsmount` virtual files (no macFUSE), and housekeeping for old
logs and stale chunk uploads.

Requires rclone >= 1.65 (tested with 1.75.1). Everything is bash 3.2 compatible and has
no build step: macOS launchd starts `/bin/bash`, so the code avoids bash 4+ features.

## Architecture

`bin/sciebo` is the single entrypoint: it sets shell options, sources the shared
libraries and command modules, dispatches, and releases the run lock on exit.

```
bin/sciebo        CLI: usage, dispatch, EXIT lock trap
lib/core.sh       paths, logging, die/usage_error, pure helpers
lib/rclone.sh     rclone discovery, config introspection, remote paths
lib/settings.sh   layered settings, config/state layout
lib/lock.sh       single-run lock (pid + process identity)
lib/manifest.sh   manifest format, parsing, index, writers
lib/ui.sh         interactive prompts and selection
lib/commands/     setup doctor discover sync list check folders mount
                  umount mounts cleanup schedule
```

Dependency direction: command modules -> libraries -> `lib/core.sh`. Commands return a
status; only `die` (exit 1) and `usage_error` (exit 2) exit directly, and modules never
call each other in-process (the folder wizard execs `bin/sciebo` per pair). Exit codes:
`0` success, `1` operational failure, `2` usage error (usage text goes to stderr).

## Configuration

```
config/settings.env            global defaults (remote name, tuning, schedule)
config/settings.local.env      local overrides (gitignored)
config/sources.conf            manual source manifest
config/roots.conf              roots for git-repo auto-discovery
config/sources.generated.conf  generated by `sciebo discover --write` (gitignored)
config/folders.conf            folder pairs chosen with `sciebo folders`
config/filters/clutter.txt     global rclone filter rules
config/filters/pair-<name>.txt per-pair excludes written by the wizard
.env                           SCIEBO_URL/USER/APP_PASSWORD (gitignored)
state/logs/                    run, mount, and launchd logs
state/locks/                   sync.lock
state/bisync/<name>/           rclone bisync bookkeeping
state/mounts/<name>.state      recorded mounts
state/mount-cache/             rclone VFS cache for read-write mounts
```

Settings precedence (low to high): `config/settings.env` < environment <
`config/settings.local.env`. `settings.env` assigns with `: "${VAR:=default}"`, so an
exported value wins; `settings.local.env` is sourced last and wins over both. Every path
is overridable for isolated runs: `SETTINGS_FILE`, `SETTINGS_LOCAL_FILE`, `ENV_FILE`, `STATE_DIR`,
`MANIFEST_FILE`, `MANIFEST_GENERATED_FILE`, `FOLDERS_FILE`, `ROOTS_FILE`, `FILTER_DIR`,
`LOG_DIR`, `LOCK_DIR`, `BISYNC_DIR`, `MOUNTS_DIR`, `MOUNT_CACHE_DIR`. `RCLONE_REMOTE`,
`REMOTE_BASE`, and `RCLONE_CONFIG` are regular settings; `RCLONE_BIN` selects the
rclone binary.

## Commands

Run `bin/sciebo` from the project root (or put it on `PATH`). `make` targets mirror the
commands; `make help` lists them, and they do not forward extra arguments.

| Command | Purpose |
| --- | --- |
| `sciebo setup` | create/update the sciebo rclone remote |
| `sciebo doctor [--offline]` | preflight checks (PASS/WARN/FAIL; `--offline` skips network) |
| `sciebo discover [--write]` | find git repositories under `roots.conf` |
| `sciebo list` | list configured sources (read-only, creates no state dirs) |
| `sciebo check` | dry run of all sources (no changes); accepts `sync` options |
| `sciebo sync [options]` | apply sync/pull/bisync for all sources |
| `sciebo folders [choose/add/list/remove]` | manage folder pairs (`choose` is the default) |
| `sciebo mount [options]` | on-demand `rclone nfsmount` |
| `sciebo umount (--folder SUB / --mountpoint PATH / --all) [--sudo]` | unmount a recorded mount |
| `sciebo mounts [--folder SUB]` | show recorded mounts |
| `sciebo cleanup (--logs / --uploads) [--apply]` | old logs / stale chunk uploads |
| `sciebo schedule install / uninstall / status` | launchd agent (`status` exits 1 when installed but not loaded) |
| `sciebo help [command]` | usage; `<command> --help` also works |

`sync` options: `--dry-run` (same as `check`), `--only NAME`, `--resync` (bisync
initialization), `--quiet`, `--no-lock`; `sciebo sync --list` remains accepted as a
compatibility alias for `list`. `sync` (unless `--no-lock`), `cleanup`, and
`discover --write` take a single-run lock in `state/locks/`; a stale lock whose pid is
gone or recycled is replaced automatically.

## Setup

1. Create an app password in sciebo: avatar -> **Settings -> Security -> Devices &
   sessions**. This is required with two-factor authentication and recommended for
   third-party clients; see <https://docs.sciebo.de/docs/sicherheit/>.
2. `cp .env.example .env` and fill in `SCIEBO_URL`, `SCIEBO_USER`
   (`<localid>@<scope>`), and `SCIEBO_APP_PASSWORD`, then run `bin/sciebo setup`
   (`make setup`). `setup` can also prompt interactively; it normalizes the URL to
   `https://<host>/remote.php/dav/files/<user>/` so Nextcloud chunked uploads work.
   Credentials are obscured into the rclone config (`~/.config/rclone/rclone.conf` by
   default) and never stored in this repository.
3. `bin/sciebo doctor` (preflight), `list` (parsed sources), `check` (dry run), `sync` (apply).

Find your institution's server URL in the [sciebo server list](https://docs.sciebo.de/docs/getting-started/webinterface/serverliste/).

## Sources

`config/sources.conf` (manual), `config/folders.conf` (wizard), and
`config/sources.generated.conf` (discovery) share one format and are all read on every
run, in that order:

```
mode | local_path | remote_subdir [ | filter_file ]
```

- `mode`: `sync`, `pull`, or `bisync`.
- `local_path`: absolute, `~`-prefixed, or relative to the project.
- `remote_subdir`: path below `sciebo:<REMOTE_BASE>/`; must not be empty, absolute,
  contain `..`, `|`, or control bytes, or have surrounding whitespace.
- `filter_file` (optional): extra filter file in `config/filters/`.

Fields are trimmed; comment (`#`) and blank lines are ignored; more than 4 fields is
invalid. Invalid entries are reported by `sciebo list` and `doctor` and fail `sciebo
sync`. Example: `sync|~/Projects/my-app|repos/my-app`.

The name shown by `sciebo list` (used for log files and bisync state) is the sanitized
`remote_subdir`: only `A-Za-z0-9._-` survive, other bytes become `_` (e.g.
`repos/my-app` -> `repos_my-app`). Duplicate names are a `FAIL` in `doctor`; `sync`
refuses duplicated `bisync` entries (shared state) and warns about duplicated
`sync`/`pull` entries (log name collisions).

### Discovery

`config/roots.conf` entries are `mode | root | remote_base | maxdepth` (default
maxdepth 3). `sciebo discover` scans each root for `.git` directories, collapses repos
nested inside other repos, and prints manifest lines; `--write` writes
`config/sources.generated.conf` and takes the run lock. Git only locates folders:
repository contents, including `.git/`, are synced like any other files. The header
reports the repository count and scanned roots; discovery exits non-zero for a missing
or invalid root/repo. `make discover` is `discover --write`.

### Folder wizard

`sciebo folders` (default subcommand `choose`; `make folders`) browses
`sciebo:<REMOTE_BASE>/` down to `FOLDERS_SCAN_DEPTH`, offers a multi-select (fzf when
installed, otherwise a numbered menu), suggests a destination per pick below
`FOLDERS_LOCAL_ROOT` (`~/sciebo` by default), and asks for a direction per folder
(`sync`, `pull`, or `bisync`; `DEFAULT_PAIR_MODE` is the default). Optional subfolder
exclusions (e.g. `node_modules/`, `__pycache__/`) are written as rules to
`config/filters/pair-<name>.txt`. The same operations are scriptable: `folders add
--remote SUB [--local PATH] [--mode MODE] [--exclude SUB] [--local-root DIR]`,
`folders list`, and `folders remove NAME`; pairs are appended to `config/folders.conf`
in the manifest format, preserving manual edits and comments.

The wizard never transfers data and never touches `sources.conf` or
`sources.generated.conf`; it writes only `folders.conf` and pair filters (a preview dry
run also writes logs under `state/`). New pairs are previewed with
`sciebo check --only NAME` unless `--no-dry-run` is passed. After adding a `bisync`
pair, run `bin/sciebo sync --resync --apply` (`make bisync-resync`) once.

## Direction semantics

- `sync` mirrors local -> sciebo. Files the remote loses land in the Nextcloud trash
  (sciebo keeps deleted files at least 7 days); no `--backup-dir` clutter is used.
- `pull` mirrors sciebo -> local. Local deletions made by a run are permanent; use with
  care.
- `bisync` is two-way. Initialize each source once with
  `bin/sciebo sync --resync --apply` (`make bisync-resync`); `--resync` can copy or
  delete files in BOTH directions, so review a dry run with `--resync` first. Conflicts
  resolve per `BISYNC_CONFLICT_RESOLVE` (`newer` by default). When you remove a bisync
  source, delete its `state/bisync/<name>` directory too.
- Dry runs modify neither side: a `pull` entry with no local directory yet and a
  `bisync` entry with no remote directory yet are reported as skipped ("first apply
  will create it"); the first apply (the `--resync` apply for `bisync`) creates them.

## Filters, `.nosync`, and cleanup

`config/filters/clutter.txt` excludes OS/editor debris (`.DS_Store`, `*.swp`, `*~`,
...); ready-to-enable groups for `node_modules/`, `__pycache__/`, build directories,
and an optional `.git/` exclusion are commented out. `sciebo doctor` parses every
`*.txt` in `config/filters/` (including wizard-written pair filters) with rclone's
`--filter-from`; syntax errors fail preflight. See [rclone filtering](https://rclone.org/filtering/).

A directory containing a `.nosync` file is skipped entirely by `sync` and `pull`;
`bisync` does not support the marker because rclone bisync rejects
`--exclude-if-present`.

Nextcloud chunked uploads (default 10 MiB) are assembled server-side under
`/remote.php/dav/uploads/<user>/` and never appear in your files tree. Nextcloud expires
abandoned uploads after 24 hours; `sciebo cleanup --uploads` reports what a purge would
delete and `--apply` removes chunk files older than `CHUNK_CLEANUP_MIN_AGE`, then trims
the emptied directories. Cleanup takes the same lock as sync, but runs on other devices
cannot be detected, which is why the age guard exists.

## Tuning and sciebo etiquette

sciebo warns that WebDAV is unsupported and asks users to keep sync intervals large and
sync only what is needed. The defaults in `config/settings.env` are deliberately gentle
(`TRANSFERS=2`, `CHECKERS=4`, `TPSLIMIT=8`); override them in
`config/settings.local.env`. Nextcloud admins can raise the chunk size to 1 GB server
side for better throughput ([Nextcloud
docs](https://docs.nextcloud.com/server/latest/admin_manual/configuration_files/big_file_upload_configuration.html#adjust-chunk-size-on-nextcloud-side)).

## Scheduling

```sh
bin/sciebo schedule install     # daily at SCHEDULE_HOUR:SCHEDULE_MINUTE
bin/sciebo schedule status      # exits 1 when installed but not loaded
bin/sciebo schedule uninstall
```

(`make schedule-install` / `schedule-status` / `schedule-uninstall` wrap these.) The
agent runs `/bin/bash <project>/bin/sciebo sync --apply --quiet` at the configured time,
with `state/logs/launchd.out.log` and `launchd.err.log` capturing output. The run lock
prevents overlap with manual runs. Set `SCHEDULE_HOUR`/`SCHEDULE_MINUTE` in
`config/settings.local.env`.

## Mount

`sciebo mount` exposes `sciebo:<REMOTE_BASE>/` via `rclone nfsmount`: files are fetched
on first access instead of being synced up front, and no macFUSE is needed (nfsmount
uses the macOS NFS client). Mount points live under `MOUNT_ROOT` (`~/sciebo-mount` by
default).

```sh
bin/sciebo mount --folder notes --ro     # read-only, no VFS cache
bin/sciebo mount --folder notes --foreground
bin/sciebo mounts
bin/sciebo umount --all                  # or --folder SUB / --mountpoint PATH
```

Read-write mounts (the default) stage opened files in a VFS cache bounded by
`MOUNT_CACHE_MAX_SIZE` (`5G` by default) under `state/mount-cache/`; `--ro` uses no
cache. macOS NFS mounts usually need admin rights, so `--sudo` may prompt for a
password. `umount` (or `make umount`, which uses `--all`) removes only mounts recorded
in `state/mounts/`, and stops the recorded rclone pid only when it is still the
`nfsmount` for that mountpoint. Mounts are strictly user-initiated, never scheduled.

## Housekeeping and tests

- `make setup` / `doctor` / `discover` / `list` / `check` / `sync` mirror the CLI
  (`make discover` adds `--write`).
- `make bisync-resync` is `sciebo sync --resync --apply`.
- `make folders` / `folders-list` are `sciebo folders choose` / `folders list`.
- `make mount` / `mount-status` / `umount` are `sciebo mount` / `mounts` / `umount --all`.
- `make cleanup-logs[-apply]` / `cleanup-uploads[-apply]` are `sciebo cleanup
  --logs|--uploads [--apply]` (older than `LOG_RETENTION_DAYS` / `CHUNK_CLEANUP_MIN_AGE`);
  `make schedule-install` / `schedule-uninstall` / `schedule-status` wrap `sciebo schedule`.
- `make lint` runs shellcheck + shfmt over the shell sources; `make test` runs
  `tests/unit.sh` (libraries, no rclone needed) and `tests/integration.sh` (end to end
  against a temporary `local` rclone remote). The tests never touch sciebo or the real
  configuration: state, manifests, and remote are redirected into a temp directory, and
  launchd is exercised only when explicitly opted in with `INTEGRATION_LAUNCHD=1`;
  leave it unset.

`sciebo doctor --offline` skips the network checks (handy before the remote exists);
`make doctor` cannot forward the flag, so run the CLI directly for offline preflights.

## Migrating from `scripts/*.sh`

If the launchd agent was installed for the old `scripts/sync.sh` entrypoint, re-run
`bin/sciebo schedule install` (`make schedule-install`) once; it rewrites the plist to
run `/bin/bash <project>/bin/sciebo sync --apply --quiet`. `sciebo doctor` and `sciebo
schedule status` warn while an installed plist still points at the old entrypoint.

A `scripts/sync.sh` compatibility shim remains for already-installed agents: it execs
`bin/sciebo` with the old dry-run-by-default behavior (`--apply` means `sync`, `--list`
means `list`). Delete the shim once `schedule install` has been re-run on every machine.

## Caveats

- Git is deliberately **not** special-cased. `.git/` is synced as files, so a sync
  while `git gc`, `fetch`, or a commit rewrites objects can leave an inconsistent
  repository in the cloud. For repos backed by a git remote this is usually
  acceptable; uncomment `- .git/` in `config/filters/clutter.txt` for working trees only.
- Running `bisync` on repositories that are actively being worked on is not recommended.
- Windows-invalid file names (`:`, `?`, `*`, trailing dots/spaces, ...) can exist on
  sciebo but may break Windows clients later.
- sciebo does not officially support WebDAV; there is no support for related issues, so keep backups.
